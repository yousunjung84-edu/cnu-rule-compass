## 1. 하드코딩 인벤토리 (실측)

핵심 발견: **검색·판정·advisories 코어는 이미 대학 중립적이다.**
실코드 하드코딩은 아래가 전부이고, 대학 고유 지식은 수집기에 몰려 있다.

| 위치 | 값 | 프로필화 |
|---|---|---|
| search.py | `ALLOWED_SOURCE_HOST="jnu.ac.kr"` | `allowed_hosts` 목록 |
| search.py | `_STOPWORDS`의 "전남대학교" | `univ_name` 파생 |
| search.py / references.py | 계층 판정 `len(source_key)>6` | `tier_rule` (학칙공포 13자리 vs 게시판 짧은 key — 대학 공통 가능성 높음, 프로필 오버라이드 허용) |
| references.py | alias 접두 제거 "전남대학교" | `name_prefixes` |
| collect_rules.py | `LIST_URL`(jnu AdminRule400) | `guideline_source` |
| collect_regulations.py | rule.jnu 목록 + law.go.kr | `regulation_source` — **korean-law MCP 경유로 교체**(도메인 검증 우회, 8/27 실측) |

## 2. 대학 프로필 스키마 초안

```json
{
  "univ_id": "knu",
  "univ_name": "경북대학교",
  "name_prefixes": ["경북대학교"],
  "regulation_source": {
    "type": "school_gazette",
    "query": "경북대학교",
    "note": "law.go.kr 학칙공포 — korean-law MCP search_decisions(domain=school)로 목록, lawService.do로 전문"
  },
  "guideline_source": { "type": "none",
    "note": "경북대는 지침급까지 학칙공포에 게시(446건 실측) — 보완 수집 불필요 가설, 파일럿에서 검증" },
  "allowed_hosts": ["law.go.kr", "knu.ac.kr"],
  "service": { "display_name": "KNU 규정 나침반", "cloud_run_service": "knu-rule-compass" },
  "known_synonyms": {}

```

`guideline_source.type` 열거: `none`(경북형) / `board_hwp`(전남형 — list_url·파서 지정)
/ `custom`(전북형 — 대학별 구현). **3유형이 곧 파일럿 순서다.**

## 3. 분리 전략 — 3안 비교

| | A. 대학별 fork | B. 멀티테넌트 단일 서버 | C. 코어 + 프로필 ✅ |
|---|---|---|---|
| 코어 개정 전파 | 9개 repo 수동 동기 — **스킬 판본 갈라짐 사고의 9배** | 즉시 | 코어 1곳 수정 → 대학별 재배포 |
| 메모리 | 대학당 1.4GB×1 | 1.4GB×9 ≈ 13GB 단일 인스턴스 — Cloud Run 한계·비용 | 대학당 인스턴스 (독립 장애) |
| 도구 계약 | 유지 | **tenant 파라미터 추가 = 계약 파괴** (승계 금지 원칙 위반) | 유지 — 소비자는 URL만 다름 |
| 운영 이관 | 쉬움(통째) | 불가능(전체가 한 덩이) | 쉬움 — 프로필+코퍼스+배포권만 이관 |
| 검증 게이트 | 대학별 복제 | 공유 | 코어 골든(공통) + 대학 골든(프로필별) 2층 |

**C 채택 제안.** 근거: ① 부서 템플릿에서 이미 검증한 패턴(공통 §A~C + 문맥 §D)의
반복 — 코어는 본부(박사)가, 프로필·운영은 각 대학이 가져갈 수 있는 구조가
"표준 제정자" 노선과 정합. ② 도구 계약 불변(절대 금지 원칙 승계).
③ 운영 이관 가능성이 개인 단일 장애점 문제의 출구.

## 6. v1 인벤토리는 전수가 아니었다 (실측으로 확인)

v1의 "코어는 이미 대학 중립적" 판단은 **낙관이었다.** 검증에서 지적된 누락을
직접 대조해 전건 확인했다.

| 누락 종속 | 실측 |
|---|---|
| 서비스 정체성 5파일 | `dashboard.py`(제목 3곳)·`answer.py`(LLM 프롬프트 "너는 전남대학교 규정 안내 도우미다")·`portal.py`·`http_server.py`(serverInfo name)·`mcp_server.py` |
| **계층 판정 이중 구현** | `references.py:235` = `len(source_key)>6` / `mcp_server.py:301` = `편제.startswith("규정집/")` — **서로 다른 기준**이 코드 두 곳에 |
| URL 식별 파라미터 | `key`(지침) vs `schlPubRulSeq`(규정) 하드코딩. `allowed_hosts`만으로 부족 |
| 규정 수집기 결합 | `admRulSeq` 추출·`chrClsCd` 기본값 `010202`·8개 분류가 JNU 제공 화면에 결합 |
| 파서 문서 관습 | 조문 제목 `()`·`【】`, 별표 `[]`·`【】`·`<>`·`〔〕`, 항목식 `1.` 순증·최소 3항목, 부칙·장절 정규식 |
| 수집 우선순위 | `CORE_KEYWORDS`·`CORE_DOMAINS`가 전남대 기준 튜닝값 |
| 보고서 | `coverage_report.py`의 전남대 전용 스냅샷·기준일·분모 |

→ **v1의 "분리 비용이 싸다"는 결론을 하향한다.** 코어 중립성은 검색·판정 알고리즘
에만 해당하고, 그 바깥(정체성·수집·파서·보고)은 전부 프로필화 대상이다.

## 8. 회귀 계약 (가장 중요한 발견)

> **"프로필화는 값의 정규화가 아니라, 기존 JNU 값에 대한 설정 주입이어야 한다."**

검증이 예측한 실패 시나리오와 그 함의:
- 대학명 접두를 **저장 시 제거**하면 → 정확 일치 검색·참조·advisory 테스트 대량 실패
- `source_key`를 `jnu:…`로 **네임스페이스화**하면 → 고정 record_id 4종
  (AGRI·HAKCHIK_30·JINGGYE_4·JINGGYE_2) + 현행 키 `3670` 검사 붕괴
  (= 이미 발급된 인용이 깨진다 — §절대 금지 위반)
- 편제를 **일반화**하면 → `규정집/연구소` 필터·`총무과 == 10` 붕괴
- 코퍼스를 **재수집**하면 → 징계 14·별표 ≥80·inbound 4 등 스냅샷 수치 흔들림

**따라서 이식 게이트는 "124 테스트 전부 통과"이며, 통과의 조건은 데이터를 손대지
않는 것이다.** 프로필은 코드가 읽는 상수를 바깥으로 빼는 작업이지, 코퍼스를
바꾸는 작업이 아니다.

## 9. 계획 수정

1. **선행 작업 신설**: 계층 판정 이중 구현(`len>6` vs `규정집/`) 일원화.
   전남대 코퍼스 17,281조문 전수 대조 결과 **두 기준 불일치 0건**(우연히 일치).
   전남대에서는 무해하지만 타 대학에서 갈라질 수 있는 잠복 결함이므로,
   프로필화 때 `tier_rule` 하나로 통합한다(회귀 위험 없음이 실측으로 확인됨).
2. 이식 순서는 유지하되 범위 확대: 정체성 5파일·URL 템플릿·파서 관습까지 프로필 주입
3. 게이트 강화: 124 테스트 + **record_id 전수 동일성 대조**(이식 전후 해시 비교)
4. 경북대 프로필은 `included_levels`·`level_classifier` 확정 후 작성 — 446건의
   레벨 분포를 먼저 실측한다(파일럿 1단계)
